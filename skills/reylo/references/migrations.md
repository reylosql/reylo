# Migrations

A project starts with `reylo migrate init`, run beside its `package.json` (never in the home directory, which it refuses), which writes its files from the database. It keeps its schema in `reylo/schema.sql` and each change to it in `reylo/migrations/<YYYYMMDDHHMMSS>_<name>.sql`, in the order `reylo/reylo.lock` lists (https://reylo.dev/migrate/docs). Commit all three. On a database another tool migrated, `init` leaves that tool's history table out (`_prisma_migrations`, Drizzle Kit's `drizzle.__drizzle_migrations`, `knex_migrations`, `schema_migrations`, `flyway_schema_history` and the like), and every comparison leaves it out too: `reylo migrate history push --url <each other database>` records `init.sql` there with the old table still in place, and dropping it later is no change to the schema: in a migration, `drop table if exists _prisma_migrations`, since a database made from `init.sql` never had it (for Drizzle Kit on Postgres, `drop table if exists drizzle.__drizzle_migrations`, then, only where nothing else is in the `drizzle` schema, `drop schema if exists drizzle`; never with `cascade`, which would drop what else is in it). `reylo migrate --help` and `reylo db --help` list each group's commands, and a flag only ever modifies a command.

- On Supabase, `init` leaves out what every new Supabase database has: the extensions in `extensions`, the grants and default privileges Supabase gives `anon`, `authenticated` and `service_role` in `public`, and the `supabase_realtime` publication. It writes only the project's changes to them, so the migrations run on any new Supabase database (a project, a branch, the local one after `supabase db reset`). Enable Realtime on a table with `alter publication supabase_realtime add table <table>` in `schema.sql`, never `create publication supabase_realtime`, which every Supabase database has already.
- To change the schema, edit `reylo/schema.sql`, then `reylo migrate new <name>`: Reylo writes the migration from what the migrations make to `schema.sql`, checked in a shadow database, never reading the database's schema. Read the file it writes, and add the data changes a schema can't say. Never write a migration's DDL by hand where `new` can write it. With nothing to change, the file is empty, for a data change.
- `new` refuses a change that drops a table or a column, or changes a column's type so that values are lost, until `--drop <table or table.column>` names it; on MySQL, a partition taken out of a table drops its rows, so `--drop <table.partition>` names it too. Name only what the change is meant to lose. A column or table that goes while one identical but for its name comes is renamed, keeping its rows. Where one goes and one comes that differs in more than its name, whatever the types, `new` can't tell a rename from a new one and refuses. It prints each pair as a `-` line and a `+` line. Once a rename is written, `new`'s summary prints it as one `~` line, its old words as `[-old-]` and its new as `{+new+}` where colour is off: `~ column posts.[-title-]{+heading+} text`. With one such pair it prints a command for a rename (`--rename <table.old>=<new>`, which casts the values to the new type; a value the database can't cast fails the migration, so fix such rows in a data migration first) and one for a drop; with several, a line for each, its `--rename` and its `--drop` side by side, and the command to add every flag from the side picked on each line to. Read each pair's names, and pick by what they mean.
- On Postgres, `new` writes a change that would block writes to a table while it reads every row in a shape that doesn't, as several files: a constraint added `not valid` then validated in the next file, a `not null` proven by a check first, an index built `concurrently` in a file of its own, a new enum value the change also uses in a file before its use. Keep the files as they are. It refuses a change that copies a table with rows (most type changes, a volatile default) until `--blocking` accepts it; for a large table, add a column, fill it in batches and swap them instead, each a migration. Each statement of a deploy waits at most half a second for a lock, then the file runs again; a migration that must wait longer starts with `set local lock_timeout = '…'`. On MySQL, `new` refuses an `alter table` that MySQL can't run on a table it keeps without blocking writes (a column's new type or a removed enum value, which copy the table, a table partitioned anew, partitions reorganized, a foreign key added) until `--blocking` accepts it, as MySQL answers the statement run with `lock=none`; a trigger that changes is one migration under `lock tables`, so no write runs without it; a partition appended to a range or list table is added in place; and a table's change runs in strict mode whatever the server's `sql_mode`, so a value the new type can't hold fails the migration and its row is kept.
- In development, `reylo migrate dev` runs the new migrations and adds them to the lock; until then a migration is a draft, free to edit. It refuses a change on the database that neither `schema.sql` nor a pending migration makes, and prints three fixes: add it to `schema.sql` and run `reylo migrate new <name>`, undo it with the `reylo run '<sql>'` it prints, or `reylo db reset`. `reylo db push` synchronizes the database with `schema.sql` without a migration, to try a change; it refuses until `reylo migrate dev` has run, and as `new` does, refuses a drop or a type change that loses values until `--drop` names it (`--rename` states a rename; `--force` accepts every destructive change at once). After a branch switch or a lock conflict (keep main's lines), run `reylo migrate dev` again. `reylo db reset` drops everything but a platform's own objects, with its rows, and runs every migration again; `reylo db wipe` deletes every row and keeps the schema and the history.
- `migrate` from `reylo` runs the migrations from code: `await migrate()` runs `reylo migrate deploy` as the command line does (`{ url }` for another database), and resolves to the names it ran. A Cloudflare Durable Object, whose SQLite database only its own code reaches, calls `migrate(ctx.storage)` in its constructor: Reylo's Vite or esbuild plugin puts the locked migrations in the bundle, in the lock's order, and each object runs those it hasn't run, records them in `__reylo_migrations`, and first refuses, running nothing, what `reylo migrate deploy` refuses in the files (a draft, a file that isn't a migration, a `schema.sql` changed since the lock) and a migration it ran that the bundle lacks, has edited, or orders differently. A Durable Object can't turn its foreign keys off, so a migration that rebuilds a table others reference fails there, or, through `on delete cascade` or `set null`, changes their rows: read each migration that drops a table.
- `reylo migrate status` checks a database against the migrations: what it ran, what's pending, whether it was changed by hand since its last migration (with the change), and every check of the files (their names, git's conflict markers, the lock's chain, a statement no shadow database could replay, and `schema.sql` against the checksum the lock holds). It reads only and needs no shadow database. It exits 1 where the database and the files aren't in step, and 0 where they are: check it before acting on a database. A `schema.sql` edited since the lock was written needs `reylo migrate new <name>`, then `reylo migrate dev`; formatting or comments alone need only `reylo migrate dev`.
- Never edit a migration the lock lists, which another database may have run: write a new one. The exception is one that failed on production, which records nothing of a failed migration: fix the file, run `reylo migrate dev` to lock it again, and deploy the fix. A migration that fails on rows the database already holds (a `check`, a foreign key or a unique index they break) needs no fix: the refusal gives a query that lists them, so fix those rows and deploy again. On Postgres the first file of the change may stay applied meanwhile, holding rows written from then on to the constraint, and `reylo migrate status` says so. Never edit `reylo/reylo.lock` by hand but to keep main's side of a conflict; `reylo migrate lock` writes it again from a database's history.
- The migration files and a database's history table are two copies of one list, and its tables say which is right. Where the files are right (a change made by hand, then written into `schema.sql` and a migration), `reylo migrate history push --url <that database>` records what its schema has, running nothing. Where that database hasn't run a migration the lock runs before the new one, it moves the new one ahead of it in the lock, as that database ran it: `reylo migrate history push` on development records the new order there, running nothing, and `reylo migrate deploy --url <that database>` runs the rest. Where that database ran every migration but one, as a database another tool kept can, it records the rest and moves the skipped one after them in the lock, for deploy to run. Past a migration that changes data, or where the two orders would end differently, it refuses and says to undo the change and deploy instead, printing the command that undoes it where `reylo run` can apply it as a migration would. A server that already ran the migrations it moved past, such as staging, is refused by `reylo migrate deploy` until it makes the change too: the refusal gives the commands. Where the database is right (a file edited or deleted, a lock lost), `reylo migrate history pull --url <that database>` writes them back as it ran them; it refuses a database changed by hand. `reylo db introspect` prints a database's schema as SQL, for a change made by hand: copy it into `schema.sql`, then `reylo migrate new <name>` writes the migration.
- In CI, and before a deploy, `reylo migrate deploy --dry-run` replays the migrations in shadow databases against `schema.sql` and the database, running nothing. In production, `reylo migrate deploy` runs what the lock lists and needs no shadow database. On Turso Cloud, or any libSQL server, `--url` takes the database's `libsql://` URL with its token, `libsql://<db>-<org>.turso.io?authToken=…`, as `@libsql/client` takes it, while `direct_url` stays on the local file the type check reads. Migrations may use libSQL's own SQL (a vector index, `alter table … alter column`): a Turso database's shadows, and the local file of a project whose SQL uses it, run on libSQL's engine. Tables named `__turso_internal_…` are Turso's engine's own (each `AUTOINCREMENT` table's counter): no command shows, compares, empties or drops them, and each stays named after its table. It refuses a database changed by hand, an added index too, showing the change: write it as a migration and record it with `reylo migrate history push`. Read a refusal, which names the fix. The development commands (`migrate dev`, `db push`, `db reset`, `db wipe`) refuse to run where `CI` is set to anything but `false`, `0` or an empty value.
- Every command, `deploy` and `status` included, refuses a migration that would reach past a shadow database, which is made on the database's own server: one that changes a role, a database, a tablespace or a server setting, and on MySQL one that names a database (`app.users`). Make roles with the server's setup, outside the migrations. Reylo doesn't check inside a Postgres `do` block, but every shadow runs one on its server, the database's own unless `shadow_url` names another, so a role made or granted in one changes the real server's roles at every dry run.
- Without `reylo/schema.sql`, the migrations are the schema: write them by hand, or change the development database and run `reylo migrate new <name>`, which writes what the database has that the migrations don't make, and refuses until every migration has run there. Without `reylo/reylo.lock`, migrations run in name order and `reylo migrate status` says so; a migration that sorts before one a database already ran is replayed in both orders, and refused where they end differently: give it a later name. Keep both files unless the project chose otherwise.
