Reylo Migrate is SQL-first schema modeling and migrations for Postgres, MySQL and SQLite.

- **Schema in SQL:** model your schema in `schema.sql`
- **Your whole database:** checks, indexes, triggers, functions, views, policies and more, all tracked
- **Preflight checks:** each migration is tried on a shadow database before it runs
- **Strict ordering:** an optional lockfile, `reylo.lock`, fixes the order migrations run in

## Schema modeling

Your schema is plain SQL in one file, not a lossy DSL like Prisma's. You write it the way you'd write it against the database:

```sql title="schema.sql"
-- tables, with check constraints
create table users (
  id integer primary key,
  email text not null check (email like '%@%'),
  verified_at timestamptz,
  updated_at timestamptz not null default now()
);

-- partial indexes
create index users_unverified on users (id) where verified_at is null;

-- custom functions
create function touch() returns trigger language plpgsql as $$
begin new.updated_at := now(); return new; end $$;

-- triggers
create trigger users_touch before update on users
  for each row execute function touch();

-- views
create view verified_users as
  select id, email from users where verified_at is not null;
```

Change any of it, and `reylo migrate new` writes the migration. It compares every kind of object each database has:

- **Postgres:** tables, columns, constraints (exclusion constraints included), indexes, generated and identity columns, views and materialized views, triggers and event triggers, functions, procedures and aggregates, enums, domains, composite and range types, partitions and table inheritance, row level security policies, sequences, schemas, extensions, grants and default privileges, comments, collations, publications, rules, extended statistics, foreign data wrappers, servers and foreign tables
- **MySQL:** tables, columns, constraints, indexes, generated columns, views, triggers, functions, procedures, events, enums, partitions, grants and comments
- **SQLite:** tables (`STRICT` and `WITHOUT ROWID` ones included), columns, constraints, indexes, generated columns, views and triggers

Operators, casts, text search configurations and a few rarer kinds are compared by name only. Write their changes by hand. Each supported kind is declared in `schema.sql` as you would on the database:

```sql tab="Tables"
create table users (
  id integer primary key,
  email text not null unique,
  name text,
  created_at timestamptz not null default now(),
  check (email like '%@%')
);

create table posts (
  id integer primary key,
  author_id integer not null references users on delete cascade,
  title text not null,
  published_at timestamptz
);
```

```sql tab="Indexes"
create unique index users_email_lower on users (lower(email));
create index posts_drafts on posts (author_id) where published_at is null;
create index posts_title_search on posts using gin (to_tsvector('english', title));
```

```sql tab="Generated columns"
create table line_items (
  id bigint generated always as identity primary key,
  price numeric not null,
  qty integer not null,
  total numeric generated always as (price * qty) stored
);
```

```sql tab="Views"

  select room, sum(total) as total from bookings group by room;

create event nightly_purge on schedule every 1 day
  do call purge_users(0);
```

How that compares with other schema-first tools:

<Callout title="Compared with Prisma">

Prisma's schema language is lossy. It covers tables and indexes, while CHECK constraints, triggers, functions, row level security, grants and comments never reach the schema file. Prisma Migrate also ignores changes to views, so each of those goes into SQL you [add to a migration by hand](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/unsupported-database-features).

</Callout>

<Callout title="Compared with Supabase">

Supabase introduced [declarative schemas](https://supabase.com/docs/guides/local-development/declarative-database-schemas) in 2025: plain SQL files in `supabase/schemas/`, diffed into migrations. They work on Postgres, for projects on Supabase. Reylo Migrate brings the same approach to MySQL and SQLite, on any host.

</Callout>

## The most advanced multi-dialect diff engine

Reylo Migrate never parses SQL text to guess what changed. It runs `schema.sql` in one shadow database, runs your migrations in another, and diffs both catalogs directly.

Each generated migration is ordered by the database's dependency records and verified on a shadow database before it is written. Retype a column that both a view and a materialized view read:

```sql title="schema.sql"
create table bookings (
  id integer primary key,
  room integer not null,
  total integer not null -- [!code --]
  total bigint not null -- [!code ++]
);

create view big_bookings as
  select id, room, total from bookings where total > 1000;

create materialized view room_totals as
  select room, sum(total) as total from bookings group by room;
```

Postgres makes that change by copying the whole table, while it blocks every read and write. So Reylo Migrate refuses until you accept it:

```terminal
$ reylo migrate new widen_total
✗ This migration rewrites bookings, copying every row while it blocks reads and writes to it
  On a table with many rows, the app's writes wait for as long as that takes.
  To change a column without copying its table, add a column, fill it in batches, then swap the two, each step a migration of its own.

  Where the table is small enough to wait for:
    reylo migrate new widen_total --blocking

Nothing was changed.
```

With `--blocking`, it writes the migration, taking each view down and putting it back around the change:

```sql title="20261104150000_widen_total.sql"
drop view big_bookings;
drop materialized view room_totals;
alter table bookings alter column total type bigint;
create view big_bookings as
  select id, room, total from bookings where total > 1000;
create materialized view room_totals as
  select room, sum(total) as total from bookings group by room;
```

Nothing that loses data is written without your say. Drop the `room` column, and the migration is refused until you name it:

```terminal
$ reylo migrate new drop_room
✗ This migration drops the column bookings.room and its data

  To drop it:
    reylo migrate new drop_room --drop bookings.room

Nothing was changed.
```

The same care goes into every migration it writes:

- **Lossy type changes** are refused the same way, such as narrowing a `numeric` column to `bigint`.
- **Renames** keep their rows when a column is replaced by one of a compatible type.
- **Constraints and indexes** never block writes on Postgres. Constraints validate in a separate migration, and indexes build concurrently.
- **Locks** on a busy table time out after 500 ms and retry, so migrations don't stall app queries.

The workflow is identical across Postgres, MySQL and SQLite: one schema file, the same commands, the same checks. The generated SQL differs because each database alters schemas differently. Give `posts` a slug and require non-empty titles:

```sql title="schema.sql"
create table posts (
  id integer primary key,
  author_id integer not null,
  title text not null,
  slug text, -- [!code ++]
  check (title <> ''), -- [!code ++]
  foreign key (author_id) references users (id)
);
```

Each database gets the migration it needs:

```sql tab="Postgres"
-- 20261104150000_post_slug.sql
alter table posts add column slug text;
alter table posts add constraint posts_title_check check (title <> '') not valid;

-- 20261104150001_post_slug_2.sql
alter table posts validate constraint posts_title_check;
```

```sql tab="MySQL"
-- 20261104150000_post_slug.sql
alter table posts
  add column slug text,
  add constraint posts_chk_1 check ((title <> _utf8mb4''));
```

```sql tab="SQLite"
-- 20261104150000_post_slug.sql
create table new_posts (
  id integer primary key,
  author_id integer not null,
  title text not null,
  slug text,
  check (title <> ''),
  foreign key (author_id) references users (id)
);
insert into new_posts (id, author_id, title) select id, author_id, title from posts;
drop table posts;
alter table new_posts rename to posts;
```

What each dialect does differently:

- **Postgres:** adds the check `not valid`, then validates it in a second migration without blocking writes.
- **MySQL:** runs DDL outside transactions, so both changes combine into one `alter table` statement.
- **SQLite:** can't add a check constraint in place, so it rebuilds the table and any referencing tables with their rows.

The same holds on hosted databases, including Supabase, Neon, PlanetScale and Turso. Platform-owned objects, such as Supabase's `auth.users`, are left alone.

<Callout title="Compared with pg-delta">

Supabase's [pg-delta](https://supabase.com/blog/declarative-schemas-2-0-pg-delta) works the same way: it "never parses SQL to understand it", resolving every state in a real Postgres. It became the default diff engine in Supabase's CLI this month, for Postgres alone. Reylo Migrate reimplements that design in Rust at parity on Postgres, and brings it to MySQL and SQLite.

</Callout>

<Callout title="Compared with Atlas">

[Atlas](https://atlasgo.io) also diffs schemas against a dev database using SQL or HCL across several dialects. Its free builds leave out views, triggers, functions, policies and drift detection. The [community build](https://atlasgo.io/community-edition) ignores changes to them, and the standard build requires [Atlas Pro](https://atlasgo.io/pricing) at $9 per user a month. Reylo Migrate is MIT licensed, with nothing held back for a paid tier.

</Callout>

<Callout title="Compared with Liquibase">

[Liquibase](https://www.liquibase.com) tracks changesets in XML, YAML or SQL, and `diff-changelog` generates them by comparing two databases. That diff omits functions, triggers and policies. It turns renamed columns into drop-and-add pairs (losing rows) and drops columns without asking. Since 5.0, Liquibase uses the FSL rather than an open source license.

</Callout>

<Callout title="Compared with Prisma and Drizzle">

Prisma and Drizzle Kit diff against their own schema models, which miss database dependencies. Retype a column that a view reads, and both generate a bare `alter table` that fails when it runs. Both emit a plain `create index` that blocks writes on busy tables. Prisma also turns renamed columns into drop-and-add pairs, and Drizzle's `generate` drops columns without asking.

Their most-upvoted open requests are for what `schema.sql` already holds:

- **Triggers:** [drizzle-team/drizzle-orm#843](https://github.com/drizzle-team/drizzle-orm/issues/843), over 500 upvotes
- **CHECK constraints:** [prisma/orm#3388](https://github.com/prisma/orm/issues/3388), nearly 300
- **Comments:** [prisma/orm#8703](https://github.com/prisma/orm/issues/8703) and [drizzle-team/drizzle-orm#886](https://github.com/drizzle-team/drizzle-orm/issues/886), over 200 each
- **Partitions:** [drizzle-team/drizzle-orm#2854](https://github.com/drizzle-team/drizzle-orm/issues/2854) and [prisma/orm#1708](https://github.com/prisma/orm/issues/1708), over 100 each
- **Generated columns:** [prisma/orm#6336](https://github.com/prisma/orm/issues/6336), over 100

</Callout>

## Schemaless mode

Delete `schema.sql`, and your migrations are your schema.

A schema file reads best in review, but migrations alone work well when an agent writes DDL. Without `schema.sql`, `reylo migrate new` drafts a migration from changes on your development database, or creates an empty file to fill in:

```terminal
$ reylo run 'alter table users add column bio text'
✓ alter table users add column bio text

$ reylo migrate new add_bio
✓ Wrote reylo/migrations/20261104140347_add_bio.sql
  + column users.bio text
```

You still see the whole schema whenever you want it, printed from the database:

```terminal
$ reylo db introspect
create table users (
  id integer not null,
  email text not null,
  bio text,
  constraint users_pkey primary key (id)
);
```

How those two modes map to frameworks teams already know:

<Callout title="Compared with Rails">

Schemaless mode matches Rails: migrations are the source of truth, and `schema.rb` is dumped from the database after they run (like `reylo db introspect`). Rails leaves every migration for you to write by hand. Reylo Migrate can draft it from the changes you made to your development database.

</Callout>

<Callout title="Compared with Django">

With `schema.sql`, Reylo Migrate works like Django's `makemigrations`, generating migrations from changes to your schema. Django's models stop at what the ORM can declare, pushing triggers and functions into hand-written `RunSQL` steps. In `schema.sql`, they are just SQL statements.

</Callout>

## Migration ordering

An optional lockfile, `reylo.lock`, lists migrations in run order, each with a chained checksum:

```yaml title="reylo.lock"
schema: c7bf681b
migrations:
  - 20261104120000_users.sql c86e9de4
  - 20261104140347_add_bio.sql 78ad08c0
```

Two branches that each add a migration conflict on `reylo.lock` in git before reaching a database. The second branch keeps `main`'s lines and runs `reylo migrate dev`, which replays its migrations after `main`'s and appends them back. Every database then runs migrations in one order, and editing a locked migration fails its checksum. The trade-off on a busy team is that parallel migration branches always conflict, even across unrelated tables.

<Callout title="Compared with Drizzle">

Drizzle Kit kept a journal, `meta/_journal.json`, through 0.x, so parallel migration branches conflicted on it. Its maintainers called that structure "completely unusable due to git incompatibility" in [a 2024 discussion](https://github.com/drizzle-team/drizzle-orm/discussions/2832). Drizzle 1.0 removes the journal and runs migrations in any order. Some teams want that, and others want the conflict. Reylo Migrate lets each team choose: keep `reylo.lock` for strict ordering, or delete it.

</Callout>

<Callout title="Compared with other tools">

Using a lockfile to force git conflicts between parallel migration branches is an established pattern:

| Tool | What holds the order | Two branches that each add a migration |
| --- | --- | --- |
| [Sentry](https://github.com/getsentry/sentry/pull/15942), since 2019 | `migrations_lockfile.txt`, each app's newest migration | Conflict in git |
| [django-linear-migrations](https://github.com/adamchainz/django-linear-migrations) | `max_migration.txt`, each app's newest migration | Conflict in git, fixed by its `rebase_migration` command |
| [Atlas](https://atlasgo.io/concepts/migration-directory-integrity) | `atlas.sum`, a hash of every file | Conflict in git, fixed by `atlas migrate rebase` |
| [Rails](https://github.com/rails/rails/issues/41128) | The newest version, in `schema.rb` | Conflict in git |
| [Sqitch](https://github.com/sqitchers/sqitch/blob/b08e5c8a773ee4ab5ea4ab7cf6f7a16c55d6994e/lib/sqitchtutorial.pod#L1185-L1210) | `sqitch.plan`, every change in order | Conflict in git, which its own tutorial turns off with git's union merge |
| [EF Core 11](https://github.com/dotnet/efcore/issues/37688) | The newest migration's ID, in the model snapshot | Conflict in git, new in 2026 |
| [Django](https://docs.djangoproject.com/en/5.2/ref/django-admin/#cmdoption-makemigrations-merge), [Alembic](https://alembic.sqlalchemy.org/en/latest/branches.html) | Each migration names its parent | Refused when migrations next run, until a merge migration joins them |
| [Prisma](https://www.prisma.io/docs/guides/v7/database/schema-changes) | Folder names, with `migration_lock.toml` holding only the database provider | No conflict in git |
| [Drizzle 1.0](https://github.com/drizzle-team/drizzle-orm/releases/tag/v1.0.0-beta.16), [dbmate](https://github.com/amacneil/dbmate/issues/159#issuecomment-698449138) | Nothing | Run in any order |

[Zenefits documented the pattern in 2015](https://web.archive.org/web/20180520172740/https://engineering.zenefits.com/2015/11/using-old-ideas-to-solve-new-problems/) after parallel migration branches kept merging cleanly and breaking `main`. It went "from having four merge errors every week to having none". Tools without a lockfile take the opposite trade-off: branches never conflict, so collisions surface only when migrations run. Even Rails sorted its full version list in `schema.rb` in 2026 to avoid merge conflicts ([rails/rails#58166](https://github.com/rails/rails/pull/58166)).

</Callout>

## Lock-free integrity

Delete `reylo.lock`, and migrations run in name order:

```terminal
$ reylo migrate status
Migrations on postgres://localhost:5432/app
  ✓ 20261104120000_users.sql    applied 2026-11-04 12:00 UTC
  ✓ 20261104140347_add_bio.sql  applied 2026-11-04 14:03 UTC
✓ Unchanged since its last migration
» With no lock, migrations run in name order
  To write one:
    reylo migrate lock
» With no lock to hold its checksum, reylo/schema.sql is checked against the migrations by a dry run
  To check it:
    reylo migrate deploy --dry-run
```

Without a lock, a merged migration can sort before one a database already ran. Reylo replays both orders on a shadow database, and refuses where they end differently:

```terminal
$ reylo migrate deploy
✗ Migration 20261105080000_no_nick.sql sorts before 20261105090000_nick.sql, which this database already ran
  Run in name order, as on a fresh database, the migrations end differently:

    --- this database
    +++ a fresh database
    + column users.nick text

  Give it a later name, so that every database runs it after 20261105090000_nick.sql:
    mv reylo/migrations/20261105080000_no_nick.sql reylo/migrations/20261105090001_no_nick.sql

Nothing was changed.
```

To go back to strict ordering, write the lock again from the order your database ran its migrations in:

```terminal
$ reylo migrate lock
✓ Wrote reylo/reylo.lock: 2 migrations, in the order this database ran them
✓ The migrations match reylo/schema.sql
```

How other migrators handle out-of-order migrations:

<Callout title="Compared with Kysely">

[Kysely's migrator](https://github.com/kysely-org/kysely/blob/master/src/migration/migrator.ts) refuses any migration that sorts before one already run. With `allowUnorderedMigrations` on, it runs every one without checking. Reylo Migrate checks whether order changes the resulting schema, and refuses only when it does.

</Callout>

<Callout title="Compared with Flyway">

[Flyway's `outOfOrder` setting](https://documentation.red-gate.com/fd/flyway-out-of-order-setting-277579015.html) is a similar binary switch. When off (the default), any migration sorting before an applied one fails validation and nothing runs. When on, it runs with a warning that the migration "may not be reproducible".

</Callout>

## A typical workflow

Write a migration, run it in development, then deploy it:

```sh
reylo migrate new add_bio    # write the next migration, from schema.sql
reylo migrate dev            # run it on your development database
reylo migrate deploy         # run what the lock lists, when you deploy
```

The two commands that run migrations do different jobs. In development, `reylo migrate dev` takes your database to whatever the current branch holds. Switch branches, and it rewinds what the other branch ran before it runs what's new:

```terminal
$ git switch feature-b
Switched to branch 'feature-b'

$ reylo migrate dev
Applying to postgres://localhost:5432/app
  ↺ 20261104120000_add_tags.sql   rewound: it isn't in the migrations
    ! Dropped tags (3 rows)
  ✓ 20261104130000_add_posts.sql  applied · 43 ms
✓ Wrote reylo/reylo.lock
```

In production, `reylo migrate deploy` runs only what the lock lists, and needs no shadow database. It stores a fingerprint of the schema with each migration, so it refuses a database someone changed by hand:

```terminal
$ reylo migrate deploy
✗ This database was changed outside its migrations

  + column users.hotfix bigint

  If a migration makes this change, record it here, running nothing:
    reylo migrate history push
  If none does, write one and run it in development, then record it here:
    reylo migrate new <name>
    reylo migrate dev
    reylo migrate history push
  To see which migrations it matches:
    reylo migrate deploy --dry-run

Nothing was changed.
```

While you prototype, skip the migration. The `reylo db push` command takes your development database straight to `schema.sql`, and `--watch` pushes again on every save:

```terminal
$ reylo db push
Pushing reylo/schema.sql to postgres://localhost:5432/app
  + alter table users add column bio text;
✓ This database matches reylo/schema.sql

$ reylo db push --watch
Watching reylo/schema.sql and reylo/migrations: each save pushes again (Ctrl-C stops)
```

Once the change is right, write its migration. Your development database already has it, so `reylo migrate dev` records it without running it again:

```terminal
$ reylo migrate new add_bio
✓ Wrote reylo/migrations/20261104140347_add_bio.sql
  + column users.bio text

$ reylo migrate dev
Applying to postgres://localhost:5432/app
  + 20261104140347_add_bio.sql  recorded: already in place
✓ Wrote reylo/reylo.lock
```

## Get started

Reylo Migrate completes the Reylo toolkit. Reylo infers types directly from SQL queries for [TypeScript](/docs) and [Rust](/rust), with no codegen, ORM or query builder.

Start from your existing database:

```bash tab="npm"
npm i -g reylo
reylo migrate init
```

```bash tab="Homebrew"
brew install reylosql/tap/reylo
reylo migrate init
```

```bash tab="curl"
curl -fsSL https://reylo.dev/install.sh | sh
reylo migrate init
```

It writes your schema and a first migration, then [the docs](/migrate/docs) take it from there:

```terminal
$ reylo migrate init
✓ Started reylo/ from postgres://localhost:5432/app
  reylo/
  ├── schema.sql          this database's schema
  ├── migrations/
  │   └── init.sql        the same, recorded as run here
  └── reylo.lock          the order the migrations run in
```

Reylo is open source, on [GitHub](https://github.com/reylosql/reylo).
